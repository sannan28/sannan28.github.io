Redis的分布式锁
     前置知识：
         锁的种类，从一个宏观的角度上区分大概有单机版锁以及分布式锁，
          单机版的锁：指的就是同一个JVM虚拟机内，synchronized以及Lock接口。
           分布式锁：
               为什么会需要分布式锁？
                   为了保证一个方法在高并发的情况下同一时间只能被一个线程执行，传统的单体应用单机部署的情况下，可以使用Java并发处理相关的api(如ReentrantLock或synchronized)进行互斥控制。但是随着业务的发展需要，原来的单体应用的系统被演化成分布式系统后，由于分布式系统多线程、多进程并且分布在不同的机器上，这样就会让原来的单体应用情况下的并发控制锁策略失效，为了解决这个问题就需要一种跨JVM的互斥机制来访问共享资源，这个就是需要分布式锁解决的问题。

            一般分布式锁需要哪些保证哪些条件
                  第一点：独占性(互斥性)。
                  第二点：这个锁需具有重入性。
                  第三点：这个锁要保证高可用。
                  第四点：加锁解锁不能张冠李戴。解锁必须要由加锁对象来解锁。
                  第五点：锁需要有过期时间，这个是为了防止死锁。
                  第六点：锁要具有非阻塞的特性，即没有获取到锁直接返回获取锁失败。
       
          Redis分布式锁是如何实现的？
                 
                 第一种：就是相对比较简单的使用setnx
                    我们可以使用setnx命令，这个命令set if not exists，即如果key不存在，才会设置它的值，否则什么也不做。两个客户端进程可以执行这个命令达到互斥，就可以实现一个分布式的锁。加锁成功的客户端，就可以去操作共享资源，比如，修改mysql的某一行数据，或者调用一个api的请求。操作完成之后呢，还涉及到要及时释放锁，给后来者让出操作共享资源的机会，
                    那么如何释放呢？也很简单，就是使用del命令删除这个key就可以了。但是它存在一个很大的问题，当客户端1拿到锁后，发生以下两种情况：
                        第一种情况：程序处理业务逻辑异常，没及时释放锁。
                        第二种情况：进程挂了，没机会释放锁。
                    发生以上两种的情况的话就会造成死锁，这个时候客户端就会一直占用锁，那么其他的其他的客户端就拿不到这把锁了，那如何解决这个问题？就是如何避免死锁？
                        比较容易想到的一个方案就是就是加锁的时候设置锁的失效时间，在redis中实现的时候，就是给这个key设置一个过期时间。这里我们假设，操作共享资源的时间不会10s，那么在加锁时，给这个key设置10s的过期时间即可:
                                 setnx lock 1
                                 expire lock 10
                        这样一来，无论客户端是否异常，这个锁都可以在10s后被自动释放，其他客户端依旧都可以再次拿到锁。但是这样呢依然还会存在问题？
                               现在的操作是加锁然后设置过期时间是2个操作，会有一种可能只执行了第一条，第二条却来不及执行的情况呢？就会出现以下情况：
                                   第一种情况就是：setnx执行成功，执行expire时由于网络问题，执行失败。
                                   第二种情况就是：setnx执行成功，redis异常宕机，expire也没有机会执行。
                                   第三种情况就是：setnx执行成功，客户端异常崩溃，expire没有机会执行。
                        总之呢，就是两条命令不能保证原子性，就会有潜在的风险导致过期时间设置失败，依旧会发生死锁这个问题，怎么办？
                               在redis2.6.12版本之前，这个问题需要想办法保证setnx和expire原子执行，还要考虑各种异常情况如何处理，但是在redis2.1612之后，redis扩展了set命令函数，使用一条函数就可以了：
                                   setnx lock 1 ex 10
                               这样也就解决了死锁的问题，也比较简单。
                               再来分析一下 还会有什么问题？
                                  首先：客户端1加锁成功，开始操作共享资源。
                                  然后：客户端1操作共享资源的时间，超过了锁的过期时间，锁被自动释放。
                                  然后：客户端2加锁成功，开始操作共享资源。
                                  最后：客户端1操作共享资源完成，释放锁，但是释放的是客户端2的锁。
                               这里呢就存在两个问题
                                    第一个问题就是：锁过期，客户端1操作共享资源耗时太久，导致锁被自动释放，之后被客户端2持有。
                                    第二个问题就是：释放别人的锁，客户端1操作完成之后，却释放客户端2的锁。
                               那么锁过期出现的原因：就是可能我们评估操作共享资的时间不准确导致的。
                                   比如共享资源的执行时间时15s，锁的失效时间时10s，那就存在锁提前过期的风险，过期时间太短，那就是增大锁的过期时间，把锁的过期时间设置为20s，这样总可以了吧？怎么说呢，这样确实能够缓解这个问题，但是依然没有办法从根本上解决这个问题。为什么呢？
                                    原因主要是在于，客户1拿到锁之后，在执行共享资源的时候，遇到场景有可能是很复杂的，比如程序内部出现异常，网络请求超时等等。既然是预估时间，也只能是大致的去计算，除非是可以在开发阶段预料到并覆盖到所有导致耗时变长的场景。但是这种也会比较困难。有更好的解决方案么？先放在下面说。



                              释放别的客户端加的锁：主要就是一个客户端释放了其他客户端持有的锁
                                  出现这个问题的关键就在于，每个客户端在释放锁的时候，都是没有校验这把锁是否还归自己所持有，所以就会发生释放别人锁的风险，这样的解锁流程很不严谨。那如何解决这个问题呢？
                                      解决的办法呢就是，在客户端加锁的时候，设置一个只有自己知道的唯一标识进去，比如说可以是自己的线程id，也可以是自己的随机id(UUID)，这我们采用UUID举例：
                                            set lock $uuid ex 20 nx(这里假设20s操作共享资源时间完全足够,先不考虑自动过期的问题。)
                                     之后，在释放锁的时候，也要优先判断这把锁是否归对应的客户端所有伪代码就可以这么写：
                                             if(redis.get(“lock”)==uuid){
                                                    redis.del(“lock”);
                                             }
                                     那么这里释放使用的死get+del两条命令，又会存在原子性的问题。那么如何解决这个问题呢？
                                        就是采用lua脚本，就是将释放锁的逻辑，写成lua脚本，让redis来执行。主要是因为redis是单线程来执行的，在执行lua脚本的时候，其他请求必须等待，直到这个lua脚本处理完成，这样一来。get+del之间就不会插入其他的命令。官网上lua的逻辑：
                                                if redis.call(“GET”,KEYS[1]) == AVG[1]
                                              then
                                                 return redis.call(“DEL”,KEYS[1])
                                               then
                                                  return 0
                                                end
                                     okk，那么经过这样的一个过程，整个加锁以及解锁就更严谨了。我们稍作总结一下就是：
                                     一个基于redis setnx实现的分布式锁的流程
                                          首先呢：客户端加锁 set lock_key uniqueid EX uniqueid EX expire_time NX。
                                          然后呢： 操作共享高兴资源。
                                           释放锁：Lua脚本，先get判断当前锁是否可以操作，在del锁。



        okk，那我们来回顾一下之前关于锁过期的问题，就是关于如何评估锁过期的问题？
            如果锁评估不好，就会存在提前过期的风险。比较简陋的方法是就是把锁的过期时间设置的长一点，降低锁提前过期的概率。这个方案其实还是很鸡肋的，并不能完全的解决问题，那怎么办呢？如果不借助第三方的组件，我们可以采用这样的方案：
             加锁的时候，先设置一个过期时间，然后我们开启一个守护线程，定时的去检测这个锁的失效时间，如果锁要过期了，操作共享资源还未完成，那就自动对锁进行续期，重新设置锁的过期时间。这种方案会比之前那种只增加过期时间的方案要好的多。
              如果采用第三方组件的方式，如果你是Java技术栈，那么还是很幸运的，已经有一个库把这些工作都封装好了：Redisson。
              Redisson是一个用java语言实现的Redis SDK客户端，在使用分布式锁的时候，它就采用了自动续期的方案来避免锁过期，这个守护线程我们一般也把它叫做看门狗线程。除此之外呢Redisson还提供了很多其他的功能
                    可重入锁、乐观锁、公平锁、读写锁、RedLock。这个sdk的api设计的非常友好，它可以像操作本地锁的方式，操作分布式锁。如果你是Java技术栈，可以直接把它用起来。
                    其实之前的解决方案都是建立在单个实例上的，并没有涉及到Redis的部署架构细节。
                      但是在实际的生产环境中，一般都会采用主从集群+哨兵的模式部署，这样的好处在于，当主库异常宕机的时候，哨兵可以实现故障自动切换，把从库提升为主库，继续提供服务，以此保证可用性。如果当主从发生切换的时候，这个分布式锁会安全么？可以构思下场景：
                         客户端1 在主库上执行set命令，加锁成功。
                         此时，主库宕机，set命令还未同步到从库上(主从复制的异步的)。
                         从库被哨兵提升为新主库，这个锁在新的主库上，丢失了！
                     怎么解决这个问题呢？ Redis作者提出一种解决方案，这个就是我们经常听到的RedLock(红锁)。

                      终于到了Redis分布式锁的精华部分！
                      Redis作者提出的RedLock是如何解决主从切换后，锁失效的问题的呢？
                      RedLock的方案基于两个前提：
                           第一个：不在采用主从+哨兵的部署模式，只部署主库。
                           第二个：主库需要部署多个，官方推荐至少5个实例。
                       也就是说想使用RedLock，至少要部署5个Redis的实例，而且都是主库，它们之间没有任何关系，都是一个个孤立的实例。
                        注意这里说的不是集群，就是部署5个简单的Redis的实例。
                        RedLock具体是如何使用的呢？
                           整体的流程是这样的，一共分为5步：
                                首先呢：就是客户端先获取【当前时间戳】t1
                                然后呢：客户端依次向这5个Redis实例发起加锁的请求(用setnx命令)，且每个请求会设置超时时间(毫秒级，要远远小于锁的有效时间)，如果某一个实例实例加锁失败(包括网络超时、锁被其它人持有等各种异常情况)，就会立即向下一个Redis实例申请加锁。
                                然后呢：如果客户端从>=3(大多数)以上Redis实例加锁成功，那就再次获取此时的时间戳t2，如果t2-t1<锁的过期时间，此时，就会认为客户端加锁成功，否则加锁失败。
                                然后呢：加锁成功，去操作共享资源(eg：修改mysql中的某一行数据，或者发起一个api)。
                                然后呢：如果加锁失败，会向全部的节点发起释放锁的请求(使用lua脚本来执行释放锁的逻辑)。

                         然后在来了解一下RedLock为什么这么设计？
                              Q1：为什么要在多个实例上加锁？
                                      本质上是为了容错，部分实例异常宕机，剩余的实例加锁成功，整个锁的服务依旧可用。
                             Q2：为什么大多数加锁成功，才算成功？
                                        其实多个Redis实例一起来用，其实就是组成了一个分布式系统，在分布式系统中，总会出现异常，所以在谈论分布式系统的问题时，需要考虑异常节点达到多少个，也不会影响整个系统的正确性。这个是分布式系统的一个容错问题，这个问题的结论是，如果存在故障节点，但是大多数节点正常，那么整个系统依旧是可以正常提供服务的。
                             Q3：为什么加锁成功后，还要计算加锁累计耗时？
                                          因为操作的是多个节点，所以耗时肯定会比操作单个实例耗时更久，而且，因为是网络请求，网络情况是复杂的，有可能存在延迟、丢包、超时等情况发生，网络请求越多，异常发生的概率就越大。所以，即使大多数节点加锁成功，但如果加锁的累计耗时已经「超过」了锁的过期时间，那此时有些实例上的锁可能已经失效了，这个锁就没有意义了。
                              Q4：为什么释放锁要释放所有节点？
                                         在某一个 Redis 节点加锁时，可能因为「网络原因」导致加锁失败。例如，客户端在一个 Redis 实例上加锁成功，但在读取响应结果时，网络问题导致读取失败，那这把锁其实已经在 Redis 上加锁成功了。所以，释放锁时，不管之前有没有加锁成功，需要释放「所有节点」的锁，以保证清理节点上「残留」的锁。


如何保证Redis和Mysql的数据一致性
    前置知识：
       在聊这个问题前，先了解一下为什么使用缓存，在高并发的场景下，数据库大多数情况都是用户并发访问的比较薄弱的环节。所以，就需要使用redis做一个缓冲操作，让请求优先访问到redis，而不是直接访问mysql数据库。这样就可以大大的缓解数据库的压力。很多的时候不单止要保存在数据库中，还需要保存到Elastic Serach、HBase、Redis等。那么如何保证redis和mysql 数据同步问题呢？
      采用阿里的开源框架Canal，它可以很方便的同步数据库的增量数据到其他的存储应用。
      

    关于Canal：
        Canal是什么？
           简而言之，canal是采用Java语言开发的用于解决数据同步的一个开源组件，主要用于mysql数据库增量日志数据的订阅、消费、和解析。

       Canal实现的原理

          在说明cannal实现的原理前，先介绍一下mysql的主从复制的流程：

          首先：当master主服务器上的数据发生改变时，则会将其改变写入到二进制事件日志文件中；
          然后：slave从服务器会在一定的时间间隔内对master主服务器上的二进制日志进行探测，探测其是否发生过改变。如果探测到master主服务的二进制事件日志发生了改变，slave就会开启一个I/O thread请求master主服务器二进制事件日志。
          然后：同时，master主服务器会对每一个I/O thread请求启动一个dump thread，用于向salve从服务器发送二进制事件日志。
          然后：slave 从服务器将接收到的二进制事件日志文件保存到自己本地中继日志问价中。
          然后：slave服务器会启动SQL thread 从中继日志中读取二进制日志，在本地进行重放，使得其数据和主服务器保持一致。
          最后：I/O thread 和SQL thread 将进入休眠的状态，等待下一次被唤醒。
       

       Canal工作原理就是模拟mysql slave的交互协议，伪装自己为mysql slave。mysql master发送dump协议，mysql master收到dump请求的时候，开始推送binary log给slave(Canal)，canal解析binary log对象。
     
    Canal的数据同步有什么作用？
       数据库镜像、数据库实时备份、索引构建和实时维护、业务cache刷新，带业务逻辑的增量数据处理。

   Canal落地的实现过程：
       注意：在配置前需要注意canal支持的mysql版本。目前支持的是基本上都是5以上的版本。

          首先是需要配置mysql：
             首先：检查下mysql的版本(select  version())。
             然后：检查当前的mysql的二进制文件的偏移量(show master status)。
             然后：查看下当前mysql是否开启二进制事件日志文件(show variables like ‘log_bin’)
             然后：开启mysql的binlog写入功能 主要就是要修改mysql conf 文件 在新的版本中mysql 不在默认指定my.cnf文件，需要自己去配置。
                  注意：如果是修改线上mysql配置文件，最好提前备份哦 嘻。
                  配置的内容：
                     log-bin:mysql-bin     #开启mysql
                     binlg-format=ROW   #选择row模式
                     server_id=1                #配置mysql replaction需要定义，不要和canal的slave id重复
                       关于binlog-format的模式：
                           ROW：除了记录sql语句之外，还会记录每个字段的变化情况，能够清楚的记录每行数据的变化历史，但会占用较多的空间。
                           STATEMENT：只记录了sql语句，但是没有记录上下文信息，在进行数据恢复的时候可能会导致数据丢失的情况。
                           MAX：比较灵活的记录，理论上说当遇到了表结构变更的时候，就会记录为statement模式，当遇到了数据变更的时候或者删除的情况下就会变为row模式。
             然后：需要重新启动mysql的服务。
             然后：再次查看 show variables like ‘log_bin’。
             最后：需要为canal授权，用于连接mysql账号。注意mysql的版本，每个版本不一致 需要使用不同的sql语法。
                           首先查看一下mysql现有的用户信息：
                               select * from mysql.user;
                            然后就开始授权：
                                DROP user 'canal'@'%';
                                create user 'canal'@'%' identified by 'canal';
                                grant all privileges on *.* TO 'canal'@'%' with grant option;
                                flush privileges;

对于缓存双写一致性的理解：
       如果redis中有数据：需要和数据库中的值相同。
       如果redis中没有数据：数据库的值需要是最新值。
 如果按照缓存的操作来区分：
      一种就是只读缓存，还有一种是读写缓存。
          说明：对于读写缓存，别名也叫同步直写策略，写缓存的时候也同步写数据库，缓存和数据库中的数据一致，对于读写缓存来说，想要保证缓存和数据库中的数据一致，就要采用同步直写策略。
                        同步直写的时机： 小数据，某一小撮热点数据，要求立刻变更的这种类型，可以前台服务降级一下，然后后台马上同步直写。
                   扩展：异步缓写时机：
                                  正常的业务，马上更新了mysql，可以在业务上容许出现一定时间后(1h)redis生效的场景。
                                  出现异常后，不得不将失败的动作重新修补，需要借助kafka 或者rabbitmq等消息中间件实现解耦后重试重写。

 数据库和缓存一致性的几种更新策略(目的就是要保证数据的最终一致性)：
     写在前面：
          以下的策略不一定百分百正确，需要酌情考虑。
          给缓存设
置过期时间，是保证最终一致性的解决方案：
               我们可以对存入缓存的数据设置过期时间，所有写的操作都以数据库为主，对于缓存操作只是尽最大努力即可。也就是说如果数据库写入成功，缓存更新失败，那么只要到达过期时间，则后面的读请求自然会从数据库里中读取新的值然后回填到缓存，达到一致性，切记以mysql的数据库写入为准。
     第一种：单线程，这样重量级的数据操作最好不要用多线程。
     第二种：存在三种情况
                        其一：先更新数据库，在更新缓存。
                                      说明：基于这种策略产生的异常问题就是先更新mysql数据，mysql更新成功了，然后更新redis，假设这个时候出现异常了，redis更新失败，这个就会导致mysql的数据和redis的数据不一致，会读到脏数据。
                        其二：先删除缓存，在更新数据库。(从数据库中读取到旧值)
                                      说明：如果写请求的处理流程是先删除在更新数据库，在一个读请求和一个写请求并发的场景可能会出现数据不一致的情况，
                                      大概的过程就是：
                                                写请求删除缓存数据，读请求查询缓存未击中，紧接着查询数据库，将返回的数据回写到缓存中，写请求更新数据库。
                                             结果就是：缓存和数据库的值不一致。
                                      问题：
                                         低并发的情况下就是，缓存中写回旧值。 
                                         高并发的情况下就是，缓存击穿。 
                                      那如何解决呢？
                                          延时双删：就是会控制读请求的从查询缓存，没查到，然后查询数据库，重写redis缓存，这个时间，在让写请求把redis的缓存在删除一次。 最主要的需要控制下第二次删除的时机。
                                              相关的一些问题？

                                                  首先呢 就是这个删除需要等多久开始执行？
                                                      解决的方式呢 就是需要自行评估读数据和写缓存操作时间。在此基础上去触发再一次删除的缓存的时机。有点鸡肋。
                            
                                                  然后呢就是如果mysql采用的是主从读写分离的架构，又会是什么什么样的？ 
                                                      整个流程大概是
                                                           首先是写请求(A)进行写操作，删除redis缓存。
                                                           写请求(A)将数据写入到数据库。
                                                           这个时候，读请求B来查询数据，发现缓存中没有。然后读请求B就去mysql的从数据库查询，这个时候呢，主从数据之间还没有同步，因此查询的就是旧的数据。
                                                           然后读请求B 就将这个旧的值重新写回到缓存。
                                                           写请求A数据写完，主从同步也完成了，但是此时还是会产生数据不一致的原因，但是依然可以采用延时双删的方式来解决这个问题。
                                                                就是通过，第二次删除的时间为预估主从同步的时间消耗 来设置。
                                                                                 
                                                  这种同步淘汰策略，导致吞吐量低怎么办？
                                                      好的处理方式呢就是会把第二次删除使用异步方式的处理，这样写的请求就不需要预估这个时间了，有的时候预估这个时间造成的吞吐量降低，这样也可以很好的解决这几个问题。

                        其三：先更新数据库，在删除缓存。(从缓存中读取到旧的值)
                                      说明：在实际的系统中，针对写请求还是推荐先更新数据库在删除缓存，但是在理论上还是会存在问题。
                                      操作过程：
                                             读请求，先查询缓存，缓存未击中，查询数据库返回。
                                             写请求，更新数据库，删除缓存。
                                             读请求，回写缓存。 
                                      结论呢就是还会存在数不一致的情况，导致应用程序从缓存中读取到旧数据。
                                      但是其实呢，这个读取到旧数据的概率还是很低的，因为通常数据库更新操作比内存操作耗时的多出几个量级，读操作的回写速度是非常速度的，通常也会在更新数据库之前完成。但是如果说这种极端的场景出现了怎么办呢？还是要想一个可以兜底的措施，就是缓存数据设置过期时间吗，通常在系统中是可以允许少量的数据短时间不一致场景出现。
                                      解决方案：
                                          重试机制+mq
                                       指导思想：
                                           1.更新数据库的数据
                                           2.数据库会把操作的信息写入binlog日志当中。
                                           3.订阅程序提取出所需要的数据以及key。
                                           4.另起一段非业务的代码，获得该信息。
                                           5.尝试删除缓存操作，发现删除失败。
                                           6.将这些信息发送给消息队列。
                                           7.重新从消息队列中获取该数据，重试操作。 
                                          说明：可以把要删除的缓存值或者是要更新的数据库值暂存到消息队列中，当程序没有能够成功的删除缓存值，或者更新数据库的时候，可以从消息队列中重新读取这些值，然后再次进行删除或者更新。如果能够成功的删除或者更新，我们就要把这些值从消息队列中删除，以免重复操作，此时，我们也可以保证数据库和缓存的数据一致了，否则还需要再次进行重试，如果重试超过一定的次数后还是没有成功，我们就需要向业务发送报错信息了，通知运维人员。
       
缓存的热点key问题
    缓存雪崩：
        首先呢 先介绍一下什么叫做缓存雪崩，在普通的缓存系统中一般redis，memcahce等中间件，我们会给缓存设置一个失效的时间，但是如果所有缓存失效的时间相同，那么在同一时间失效时，所有的系统的请求都会发送到数据库层，数据库可能无法承受如此大的压力导致系统崩溃。
          那么如何解决这个问题呢？
              处理的方式呢分成三个阶段，事前redis缓存集群实现高可用(主从或者Redis Cluster)，事中就会采用本地缓存+限流组件，事后呢就是会通过redis的持久化机制，尽快恢复缓存集群，一旦重启，自动从磁盘上加载数据恢复内存中的数据。
   
    缓存穿透：
         同样的，首先还是会介绍一下什么叫做缓存穿透，在请求数据的时候，在缓存层和数据库层面都没有查找到符合条件的数据，也就是说，在缓存层以及数据库层都没有命中数据，那么这种情况就叫做缓存穿透。
           那么如何解决这个问题呢？
              方案1：就是采用空对象缓存或者缺省值。
                   说明：一旦发生缓存穿透，我么就可以针对查询的数据，在redis中缓存一个空值或者和业务方协商确定的缺省值，紧接着，后续应用再次发送请求的进行查询的时候，就可以直接从redis中读取控制或者设置的缺省值，返回给业务方，避免了把大量请求发送给数据库处理，保持数据库的正常运行。
              方案2：Google布隆过滤器Guava解决缓存穿透。
              方案3：Redis布隆过滤器解决缓存穿透。

   缓存击穿：
        同样的还是先介绍一下什么叫做缓存击穿，缓存击穿实际上是缓存雪崩的一个特例，由于系统中对这些热点的数据也存在失效时间，在热点的缓存到达失效时间时，此时依然会有大量的请求到达我们的服务器，没有了缓存层的保护，这些请求同样会到达数据库从而引起故障。击穿和雪崩的区别在于击穿主要的是针对热点数据，而雪崩是全部数据。
       那么如何解决这个问题呢？
           策略1：互斥更新，随机退避。
                说明：
                      思路：
                          假设场景是百分之百的高并发，绝对不可以用mysql实现。
                          首先肯定是需要把mysql里面参与活动的数据信息进行预热，也就是放到redis里面，一般会采用定时任务来上线活动还是下线取消。
                           要求的话 需要支持分页查询，一页20条记录。

                           采用定时任务去去更新热点数据 对热点数据开启两份缓存(A,B),这两份缓存的更新方式是，先更新B缓存 ，缓存时间为20天，然后在更新A缓存，时间为15天，在查询热点数据的时候，会优先查询A缓存，如果A缓存中不存在，在查询B缓存中断额热点数据，这样就能稍微保证一下在更新热点数据的时候 会有请求直接打到数据库上了。
                            
                
           策略2：对于热点频繁访问的热点key，简单粗暴的方式就是不设置过期时间。
           策略3：互斥独占锁防止击穿。
           策略4：业务上规避，提前关闭入口。但是这种方式是比较糙的。

redis 经典五种数据类型
     string
       
     hash
       hash的编码格式：主要ziplist + hashtable 组成的。默认使用的是ziplist  需要注意的点ziplist数据结构可以转变成hashtable  但是反过来是不可以，即hashtable 变成ziplist。
         可以使用如下命令来查看：
             -> config get hash*
                   hash-max-ziplist-entries 512   含义就是：使用压缩列表保存的时哈希集合中的最大元素个数。
                   hash-max-ziplist-value 64       含义就是：使用压缩列表保存的时哈希集合中单个元素的最大长度。
                     说明：如果hash中的元素个数超过512 或者单个元素的长度超过64。

          流程：
             首先是先遍历对象列表是否结束：
                 如果结束了，
                     会判断：hash编码格式为ziplist&&hash的元素个数大于hash-max-ziplist-entries，那么ziplist会直接转换为hashtable，如果不是，那么数据结构的类型不需要转换。此次流程直接结束。
                 如果没有结束，
                     会判断：对象的编码格式是raw 或者embstr && 对象的字符串长度是否大于hash-max-ziplist-value，如果满足这个条件，ziplist—>hashtable，如果不是就需要重新遍历对象列表。
  
           关于ziplist详细介绍：
                ziplist压缩列表是一种紧凑的编码格式，总体思想采用的是时间换空间，主要是以读写性能为代价，来换取极高的内存空间利用率，因此只会用于字段个数比较少，且字段值比较少的场景，压缩列表内存利用率极高的原因与其连续内存的特性是分不开的。
                所以就是说，如果一个hash对象，只包含少量的键值对，并且键和值要么元素的数量比较少，要么就是每个元素的长度比较少字符串。那么它会用ziplist作为底层实现。
              ziplist数据结构：
                zlbytes—zltail— zlen—entry1—…—entryN—zlend     
                  zlbytes：代表的是压缩表占用内存字节数。
                  zltail：尾节点至起始节点的偏移量。
                  zlen：节点数量。
                  entry：压缩列表包含的各个节点。节点的长度由节点的内容决定。
                  zlend：特殊的标记，标记压缩列表末端。
                其中entry的数据结构包含一下几个属性：
                    prevrawlensize：上一个链表节点占用的长度。
                    prevrawlen：存储上一个链表节点长度数值所需要的字节数。
                    lensize：存储当前节点链表长度数值所需要的字节数。
                    len：当前链表节点占用的长度。
                    headersize：当前链表节点的头部大小(prevrawlensize+lensize)，即非数据域的大小。
                    encoding：编码格式。
                    p：压缩链表以字符串的形式保存，该指针指向当前节点的起始位置。

             关于ziplist的面试题：
                   为什么已经有链表了，还会在出来一个压缩链表？
                       第一点，首先普通的双向链表会有两个指针(前后指针)，在存储数据很小的情况下， 我们实际存储的数据的大小可能还没有指针占用的内存大，得不偿失，ziplist是一个特殊的双向链表，内部没有维护双向指针prev next而是存储了上一个entry的长度和当前entry的长度，通过长度推算下一个元素在什么地方。牺牲读取性能，获得高效的存储空间，因为(简短字符串的情况)存储指针比存储的entry长度更废内存。这是典型时间换空间的方式。
                       第二点，基于链表自身的特点，链表在内存中一般不是连续的，遍历相对比较慢，而ziplist可以很好的解决这个问题，普通的数组遍历是根据数组里面存储的数据类型找到下一个元素，但是ziplist每个节点的长度可以是不一样的，而我们面对不同长度的节点又不可能使用函数，多以ziplist只好将一些必要的偏移量信息直接记录在每一个节点里，这样的话就可以访问当前节点的上一个节点和下一下节点了。
                      第三点就是，头节点里会直接存储当前链表标的长度，因此获取链表的长度时就不需要在遍历整个链表，直接使用头结点的中的len值就好。时间复杂度是O(1)。

       set
         set的编码格式主要是以inset+hashtable存世set，如果说元素是int类型，就用inset来存储。如果不是整数类型，就会用hashtable(数组+链表）key就是元素的值，value为null。
         —>config get set*
               “set-max-inset-entries” // 使用intset保存的时set集合中的最大元素个数
               “512”
                   说明：集合元素都是longloong类型，并且元素的个数<=set-max-inset-entries，那么编码就是inset，反之就是hashtable  默认是512
     zset
        zset的编码格式主要是以ziplist+skiplist作为有序集合的底层实现，当有序集合中包含的元素数量超过服务器的属性server.zset_max_ziplist_entries的值，默认是128，或者就是有序集合红的元素长度超过大于服务器的属性server.zset_max_ziplist_value的值默认是64。
      关于skiplist的
           优点：是一个典型的空间换取时间的思想，而且只有在数据量较大的情况下才能体现出来优势，适用的场景也最好是读多写少的情况，
           缺点：适用范围比较有限，维护成本相对要高，新增删除需要把所有的索引都更新一遍，在新增和删除过程中的更新，时间复杂度也会是O(log n)	。
